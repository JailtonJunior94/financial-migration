# Relatório de Execução - Tarefa 6.0

## Tarefa

**6.0 - Implementar cadastro prévio de cartões e bindings remotos**

Implementar o fluxo que reconhece cartões por chave de negócio, faz lookup no destino, cria apenas quando necessário e persiste o binding legado-remoto localmente para uso posterior na publicação de transações.

## Resumo da Implementação

Foram implementados a chave de negócio determinística (reutilizando a já existente), o adapter HTTP de lookup/criação de cartões, o store local de bindings remotos e o use case de cadastro prévio de cartões. Os tipos de domínio `ConsolidatedCard` e `PublishableCard` foram ajustados para refletir o contrato real da API destino observado no repositório `mecontrola`.

### Arquivos criados

#### Domínio

- `src/domain/publication/card-idempotency.ts`
  - Função `buildCardIdempotencyKey` que produz chave de idempotência determinística por `userId` + `businessKey`.

#### Adapter HTTP

- `src/adapters/http/mecontrola-cards.ts`
  - Implementação de `CardTargetPort` para a API destino.
  - `findByBusinessKey`: lista cartões com paginação e encontra correspondência pela mesma chave de negócio normalizada.
  - `create`: envia `POST /api/v1/cards` com `nickname`, `bank`, `due_day` e `Idempotency-Key`.
  - Valida respostas com Zod e propaga `ApplicationError` em falhas de contrato ou HTTP.

#### Adapter de persistência

- `src/adapters/checkpoint/file-remote-binding-store.ts`
  - Implementação de `RemoteBindingStorePort` usando diretório com um arquivo JSON por binding.
  - Nome do arquivo derivado de `database-table-primaryKey` para rastreabilidade direta.

#### Caso de uso

- `src/application/use-cases/publish-cards.ts`
  - Orquestra o cadastro prévio: binding local -> lookup remoto -> criação remota -> persistência de binding.
  - Evita duplicidade no destino e persiste vínculos para múltiplas referências legadas do mesmo cartão.
  - Emite `ReviewableIssue` para cartões consolidados com dados insuficientes e retorna erro tipado em falhas de integração.

### Arquivos alterados

- `src/domain/consolidation/types.ts`
  - `ConsolidatedCard` agora possui `nickname`, `bank` e `dueDay` (além de `closingDay` e `expirationDate` opcionais), alinhando com o contrato real de criação de cartões.

- `src/domain/publication/types.ts`
  - `PublishableCard` ajustado para `nickname`, `bank`, `dueDay` e `closingDay` opcional, removendo campos sem correspondência no contrato real (`displayName`, `expirationDate`).

### Arquivos de teste criados

- `test/application/publish-cards.test.ts`
  - Testes unitários do use case: criação, skip por binding local, skip por lookup remoto, múltiplas referências legadas, validação de campos obrigatórios e falha de integração.

- `test/adapters/file-remote-binding-store.test.ts`
  - Testes de integração com filesystem temporário: persistência, leitura, sobrescrita e múltiplas referências.

- `test/integration/mecontrola-cards.test.ts`
  - Testes de integração HTTP com servidor fake local: lookup, paginação, criação com headers/body esperados e cenários de erro.

## Decisões e Observações

- O contrato real de criação de cartões no destino exige `nickname`, `bank` e `due_day`; `closing_day` não faz parte do payload de criação, mas é retornado na resposta. Os tipos `ConsolidatedCard` e `PublishableCard` foram ajustados para refletir isso, com base na collection Postman e no código do repositório `mecontrola`.
- O lookup por chave de negócio no destino é feito por listagem paginada, já que a API não expõe filtro direto por chave canônica. A correspondência usa a mesma normalização da chave de negócio do domínio.
- O store de bindings utiliza um arquivo JSON por referência legada (`${database}-${table}-${primaryKey}.json`) dentro do diretório configurado, conforme o padrão `tmp/remote-bindings/*.json` da techspec.
- Não foram introduzidas dependências novas.
